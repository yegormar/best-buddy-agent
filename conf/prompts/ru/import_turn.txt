СКРИПТОВЫЙ ИМПОРТ ПАМЯТИ (не живой чат)

Вы загружаете заранее извлечённые факты интервью в долговременную память.
Блок ниже — не живое сообщение пользователя, а пакет для пакетного импорта.
В нём могут быть заголовки MERGED_CONVERSATION, секции === CHUNK ... === и
DRAFT EXTRACTION с блоками Entities:, Facts: и Relations:. Обработайте ВСЕ
фрагменты (chunk) и ВСЕ разделы пакета.

ПОРЯДОК РАБОТЫ (строго):
Фаза 1 — save_memory для каждой сущности и каждого факта.
Фаза 2 — link_memories для каждой допустимой связи (только после фазы 1).

Фаза 1 — правила save_memory:
- Прочитайте каждую строку в Entities: и каждый пункт под Facts:.
- РАССКАЗЧИК → User (обязательно; важнее написания в Entities):
  Рассказчик интервью ВСЕГДА сохраняется как subject "User" (category: person).
  НЕ создавайте отдельную сущность по метке рассказчика из Entities: / Facts:.
  Объедините все факты о рассказчике в ОДИН вызов save_memory с subject="User".
  Метки рассказчика в файле (на любом языке) сопоставляйте с User — не копируйте
  их как subject.
- Для каждой другой отдельной сущности один вызов save_memory с сфокусированным content.
  Объедините все факты из Facts: об одном субъекте в content этой сущности.
- Если в факте есть цитата (Цитата:), включите её дословно в content,
  например: Цитата: «...»
- Выберите category по смыслу: person, place, event, fact, preference и т.д.
  Только допустимые категории: person, preference, fact, event, place, project,
  skill, organisation, concept, media, self_knowledge — не «personal» и не «group».
  Для групповой метки (несколько людей одним именем) используйте category person.
- В КАЖДОМ вызове save_memory укажите tags "conversation:{conversation_id}".
- Каноническое написание subject — как в списке Entities:, КРОМЕ рассказчика
  (всегда subject "User", см. выше).
  Если в Relations: другое написание (регистр, пробелы), для save_memory берите
  написание из Entities: (не рассказчик).
- Перед фазой 2 пройдите каждую строку Relations: каждый конечный пункт, кроме
  рассказчика, должен уже существовать после save_memory. Если имя есть только
  в Relations: или Facts:, но не в Entities:, создайте его в фазе 1 (category по смыслу).

Фаза 2 — правила link_memories:
- Передавайте имена субъектов из save_memory (не hex id).
- В source_id и target_id используйте "User", когда в Relations: указан рассказчик —
  не сырую метку рассказчика из файла.
- Переведите описание связи в конкретный relation_type (snake_case).
  Никогда не используйте related_to, associated_with, connected_to, linked_to,
  describes, differs_from, contrasts_with и подобные описательные типы.

Справочник типов связей (свободный текст → relation_type):
  был на / посещал / проводил время на                         → visits
  жил в / останавливался / снимал                              → lives_in
  родился в                                                    → born_in
  работал / работал на                                         → works_at
  отец / мать / брат / супруг / ребёнок                        → father_of, mother_of,
                                                               sibling_of, spouse_of, child_of
  бабушка / дедушка / прародитель                                → grandmother_of, grandfather_of,
                                                               grandparent_of (предок → потомок)
  друг / коллега / знает                                       → friend_of, colleague_of, knows
  предпочитает / нравится / не нравится                        → prefers, enjoys, dislikes
  имеет / владеет (объект)                                     → uses или owns (не голый "has")
  одно лицо под разными именами                                → один save_memory; доп. имена
                                                               в content/aliases — не same_person

Не вызывайте link_memories, если строка Relations: — не типизированная связь:
  - скобки только характеризуют объект («описывал как …», «называл …»)
  - скобки только противопоставляют («в отличие от …»)
    без указания типа связи
  - нельзя выбрать конкретный relation_type

Ориентиры (подставляйте имена из payload — не придумывайте сущности):
  - ПРОПУСТИТЬ: только контраст в скобках
  - ПРОПУСТИТЬ: только характеристика в скобках
  - СВЯЗАТЬ: явное действие или роль (посещал, жил, работал, родство) И оба конца
    уже сохранены — тип из справочника выше

Направление: source выполняет действие или несёт роль.
  Родство: родитель или прародитель — source; ребёнок или внук — target
  (не ставьте типы прародителя с User в роли source).
  Шаблон: source_id='User', target_id='<место или человек из save_memory>',
  relation_type='<конкретный тип из справочника>'.

Запрещено: delete_memory, write_file, trigger_workflow, explore_connections,
update_memory (этот ход только на добавление).

link_memories, например: «Сохранено 8 сущностей и создано 4 связи.»
